# Comment discipline

One rule, three ways to fail it.

> A comment states what IS. It earns its existence before its size. It is understood on the first read or it is deleted.

## Default: no comment

Write the code first, then ask: **what does this comment say that the code does not?** No answer means delete. That alone kills every doc comment that restates a name and a type — `// RecipeNotFoundError provides context about which recipe was not found` tells a reader nothing the identifier didn't.

Then raise the bar: **would a competent reader introduce a bug without this?** True-and-mildly-interesting is not enough.

## Axis 1 — what it says: what IS, never the journey

No changelog. No comparison with the option not taken. No "turns out", no "the problem was", no "we used to". The reader cares what the code does now. Why B beat A belongs in the commit message, where it stays accurate.

```go
// mainPhoto decodes from either a bare URL string or a full Photo object. ← fine
// MarshalJSON emits mainPhoto as a URL string, which is the exact reason
// imported recipes could not be saved before this existed.                ← journey
```

A regression test is the one place the journey is the subject: `// Guards against …` states what the test *is*. Keep it to the invariant, not the incident report.

## Axis 2 — how much it says: count the file, not the comment

One line where it has earned one. Two for a genuine trap. Never a paragraph at the head of a file.

Per-comment judgement is the trap. Every comment can survive on its own merits while the file drowns. **Two survivors in a service file beat eight hedged ones.** When they are all big, none get read; none get read, so none get fixed, and they rot. That is strictly worse than no comments.

## Axis 3 — how it reads: plainly, first time

Compression is not economy. A comment squeezed into allusive clauses looks disciplined and costs the reader more than it gives.

```dart
// Neither survives the auth gate below: …   ← "neither" refers to nothing yet
// The cached profile skips the auth gate.   ← names the subject
```

Name the subject. One thought per comment. Sacrifice grammar for clarity, never clarity for brevity. **If it needs a second read, delete it rather than compress it.**

## Never name a file or symbol

They move; the comment does not. This is the highest-rot form there is. Name the thing, not where it lives. Package import paths and URLs are stable enough to name.

## Go doc comments

Godoc convention wants exported identifiers documented, and `NewX`/`Probe`/service doors here have that. The convention is not a licence to restate: a doc comment that only re-reads the signature fails the default test above. Document the contract the caller cannot see — what an error means, what a nil returns, which invariant the constructor assumes. If there is nothing of that kind to say, the identifier's name was the documentation.

## Dart and Flutter

`///` on a widget earns its place the same way. Never annotate what the layout obviously is; the widget-per-file rule and the class name carry that. Domain models generated by freezed need no field commentary — `@JsonKey` already states the FE↔BE bridge.

## Config templates

The values ARE the documentation. Comment only what cannot be inferred:

- what an empty value means
- which magic string is live
- a don't-commit warning
- a coupling the reader cannot see from here

One comment over a run of related keys, not one per key. The same applies to SQL migrations and `queries/*.sql`: the query's name and its `-- name:` annotation say what it does.

## Reviewing and trimming

Trimming pre-existing bloat in a file you are already touching is welcome, not scope creep.

Watch for the same bloat in prose written **about** rules — skill files, `docs/`, `AGENTS.md` — not only in code.

## The mechanically-checkable part

Three shapes are wrong every time, so a linter holds them. `tool/commentlint` covers Go and Dart alike and runs as the **"Comments: Lint"** CI job — a violation fails the build.

| Check | Rejects |
| --- | --- |
| `max-comment-run` | a run of standalone comment lines taller than 2 |
| `no-narration` | journey phrases — "turns out", "we used to", "the bug was", "originally", "in hindsight", … |
| `no-path-pointer` | source paths and `recipe.go:42` line pointers (URLs exempt) |

Lint directives, build tags, `// ignore:` pragmas and generator headers are machine-readable, not prose — they are exempt, and generated files are not scanned. A trailing comment beside code never joins a standalone run.

Run it with `go run ./tool/commentlint` before pushing. There is no baseline: a comment is deleted or rewritten faster than it is grandfathered.

Lint enforces the shape. Whether a comment earns its place stays the reviewer's call.
